# 최종 접근 미니게임 설계

## 배경과 목적

AstroGame은 중학교 천체 수업에서 학생 한 명당 기기 한 대로 쓰일 예정이다.
현재 탐사 루프는 사진을 찍어 포인트를 모으고, 그 포인트로 장비를 사서,
"탐사 기지"에서 버튼 한 번으로 탐사를 보내는 식이다. 결과는 장비로
정해지는 확률(`getMissionSuccessChance`)을 굴려 성공/실패가 자동으로
갈린다.

(이 문서는 초안에서 "미니게임 결과가 기존 확률에 보너스/페널티로
더해진다"는 설계로 시작했으나, 아래 "설계가 바뀐 이유"에서 보듯 최종
판정 방식 자체를 바꾸는 쪽으로 정리됐다.)

사용자(교사)가 이 루프를 "단순하다"고 느껴, 탐사를 보내는 순간에 학생이
직접 손으로 조작하는 구간을 넣고 싶어 한다. 특히 빨리 끝낸 학생이 남는
시간에 다시 해볼 거리가 되었으면 한다.

브레인스토밍 중 나온 핵심 통찰: 탐사 대상은 두 종류로 나뉜다 — 단단한
표면이 있는 암석형 천체(달·수성·금성·화성)와, 표면이 없는 가스/얼음
거대행성(목성·토성·천왕성·해왕성). 하나의 "착륙" 미니게임으로 뭉뚱그리면
가스행성에서 맥락이 안 맞으므로, 두 가지 변형으로 나눈다.

### 설계가 바뀐 이유

초안을 구현자 검토에 돌렸을 때 두 가지 질문이 나왔다:

1. 미니게임 결과가 안 보이고 조용히 확률만 바꾸면, 학생이 완벽하게
   착륙하고도 주사위에서 져서 "탐사 실패"를 볼 수 있다 — 자기 조작이
   결과에 영향을 줬는지 알 길이 없다.
2. 반대로 착륙 미니게임에서 추락했는데(미니게임 실패) 최종 결과는
   무작위로 "🎉 탐사 성공!"이 뜰 수도 있다 — 서사가 안 맞는다.

사용자가 내린 결론: **확률 굴리기 자체를 없애고, 미니게임 결과가 곧
최종 성공/실패가 되도록 한다.** 대신 장비(우주선·탐사선·아이템)는 "그
대상에 도전할 자격이 있는가"를 가르는 조건으로 쓴다 — 적정 조합이
없으면 탐사 버튼 자체가 비활성화된다. 이러면 위 두 질문이 설계상
자연스럽게 해소된다: 미니게임이 곧 결과이니 둘이 어긋날 수가 없다.

## 목표

- 탐사 비행 연출의 "최종 접근" 단계(탐사선이 분리되어 목표에 도달하는
  순간)에 학생이 직접 조작하는 구간을 넣는다.
- 암석형 천체 4곳에는 **착륙 미니게임**, 가스/얼음 거대행성 4곳에는
  **궤도 진입 미니게임**을 각각 적용한다.
- 결과는 성공/실패 2단계로만 가른다.
- **장비는 "자격 조건"으로 쓴다.** 적정한 우주선·탐사선·아이템 조합을
  갖추지 못하면 그 대상으로는 탐사 자체를 시작할 수 없다 (지금처럼
  확률을 깎아서 "되긴 하지만 잘 안 되는" 식이 아니라, 아예 막는다).
- **최종 성공/실패는 미니게임 결과가 그대로 결정한다.** 기존의
  장비 기반 확률 굴리기(`Math.random() < chance`)는 없앤다. 장비는
  대신 미니게임 자체를 더 쉽게/너그럽게 만드는 쪽으로 작용한다 (아래
  "최종 판정" 참고).
- 재도전에 비용이 들지 않는 기존 구조를 그대로 유지한다 — 실패해도
  부담 없이 바로 다시 시도할 수 있어야 한다 (수업 중 반복 학습).
- 키보드 입력을 전제로 한다 (학생 기기에 키보드 있음 확인됨).

## 비목표

- 실제 궤도역학/착륙 물리를 시뮬레이션하지 않는다. "그럴듯한 느낌"이면
  충분하다.
- 미니게임 성과로 별도 포인트를 주지 않는다 — 최종 성공/실패 판정에만
  영향.
- 탐사 대상 목록을 늘리거나 줄이지 않는다. 현재 탐사 기지 화면에 있는
  8개 대상(달·수성·금성·화성·목성·토성·천왕성·해왕성)이 전부다.
- 기존 포인트 경제·장비 구매 시스템은 건드리지 않는다.

## 안티 목표

- 중학생 기준으로 조작이 너무 어렵거나 좌절감을 주면 안 된다 — 특히
  가스행성 쪽 타이밍 창이 너무 좁아서 여러 번 실패가 반복되는 일은
  피한다.
- 기존에 이미 공들여 맞춰놓은 비행 연출 타이밍(`exploration-mission.ts`의
  `PHASE_SCHEDULE_MS`, `SHIP_TRAVEL_MS` 등 — 커밋 로그에 타이밍 버그를
  고친 이력이 있음)을 건드리거나 깨뜨리지 않는다. 미니게임은 그 타임라인
  *뒤에* 삽입되는 별도 단계로 넣는다.
- 미니게임이 탐사 경제와 분리된 "딴 게임"처럼 느껴지면 안 된다 — 미니게임
  결과와 최종 결과가 어긋나는 일이 없어야 한다 (이제 둘이 같은 것이므로
  구조적으로 보장됨).
- 장비를 "자격 조건"으로 바꾸면서, 돈을 더 써도 탐사가 아예 안 되는
  막막한 상황을 만들면 안 된다 — 필요한 조합을 포인트 경제 안에서
  현실적으로 모을 수 있어야 한다 (기존 비용 체계를 유지하는 선에서).

## 결정된 설계

### 탐사 가능 조건 (자격 게이트)

지금도 각 대상은 해당 우주선 단계(`SHIP_TIERS`의 tier)를 보유해야만
탐사 버튼이 활성화된다 (스크린샷상 "🔒 우주선 단계 부족"). 이 게이트를
확장한다:

- 가스/얼음 거대행성 4곳(목성·토성·천왕성·해왕성)은 **탐사선 2단계
  이상**도 함께 요구한다. 탐사선 2단계("궤도 관측선") 설명에 이미
  "가스 행성에도 투입 가능"이라고 되어 있고, 1단계("기본 로버")는
  바퀴로 움직이는 로버라 애초에 가스 행성에 맞지 않는다 — 기존 플레이버
  텍스트에 이미 깔려 있던 제약을 실제 게이트로 승격하는 것.
- 우주선 단계 게이트는 지금과 동일하게 유지 (대상별 필요 tier는
  `SHIP_TIERS`에 이미 정의됨).
- 부품(`PARTS`: 부스터/생명유지 모듈/정밀 관측 장비)을 추가 게이트로
  쓸지는 구현자가 판단한다 — 최소한 위 두 조건(우주선 단계 + 가스
  행성의 탐사선 단계)은 반드시 게이트여야 한다.

버튼이 잠겨 있을 때의 안내 문구("🔒 우주선 단계 부족" 등)는 어떤
조건이 부족한지 보여주는 지금 패턴을 그대로 확장해서 쓴다.

### 삽입 지점

`exploration-mission.ts`의 `createMissionRunner`가 반환하는 함수는 현재
`FLIGHT_DURATION_MS` 뒤에 바로 `resolveMission(designation, crewed)`를
호출한다 (파일 167-171행). 이 지점을 아래처럼 바꾼다:

1. 비행 연출(발사~탐사선 도착)은 지금과 완전히 동일하게 유지.
2. 탐사선이 도착하면, 비행 오버레이(`#mission-flight-overlay`)를 닫기
   전에 새 미니게임 오버레이를 띄운다.
3. 미니게임이 끝나면(성공/실패), 그 결과를 그대로 최종 성공/실패로
   삼아 결과 화면을 띄운다 — 확률을 다시 굴리지 않는다.

### 두 가지 미니게임

**착륙 (달·수성·금성·화성)**: 수직 게이지로 고도/하강 속도를 보여준다.
`Space`를 누르고 있으면 역추진(하강 속도 감소), 떼면 중력으로 다시
가속된다. 고도가 0에 닿는 순간 하강 속도가 "안전 착륙 속도" 이하면 성공.
천체마다 중력(가속도)과 안전 속도 임계값을 다르게 줘서, 달은 널널하게,
수성·금성은 더 빡빡하게 — 실제 중력 차이를 몸으로 느끼게 한다.

**궤도 진입 (목성·토성·천왕성·해왕성)**: 가로로 움직이는 바늘이 게이지를
왕복한다. 가운데 "안전 진입 구간"이 표시되고, 바늘이 그 구간 안에 있을
때 `Space`를 누르면 성공. 너무 일찍 누르면 "대기에 끌려 들어감", 너무
늦으면 "궤도를 벗어나 우주로 날아감" — 이 서사로 "왜 가스행성은 착륙이
안 되는가"를 자연스럽게 전달한다. 목성은 구간을 더 좁게/바늘을 더
빠르게 해서 긴장감을 주고, 나머지는 상대적으로 여유 있게.

둘 다 제한 시간을 둔다(대략 6~8초). 시간 안에 아무 입력이 없으면 실패
처리한다 (멈춰서 진행이 안 되는 상황 방지).

### 최종 판정

`getMissionSuccessChance`로 확률을 굴리던 `resolveMission`의 로직
(`Math.random() < getMissionSuccessChance(designation)`, 69행)을
없애고, 미니게임이 돌려주는 성공/실패 결과를 그대로 쓴다. 성공 시
결과 화면과 점수 지급(`exploreTarget`)은 지금과 동일하게 진행하고,
실패 시 결과 화면도 지금과 동일하게 띄운다 — 달라지는 건 "무엇이
성공/실패를 정하는가" 뿐이다.

실패 문구(`MISSION_FAILURE_REASONS`)는 지금처럼 완전히 무작위인 대신,
그 미니게임에서 실제로 무엇이 잘못됐는지에 맞춰 고른다 (예: 착륙에서
속도 초과로 실패했으면 "충돌" 계열 문구, 궤도 진입에서 타이밍을 놓쳤으면
"궤도 이탈/대기권 진입" 계열 문구). 정확히 몇 종류를 나눌지는 구현자가
정한다 — 다만 "완벽하게 착륙했는데 통신 두절로 실패했다" 같은, 미니게임
내용과 무관한 문구가 뜨는 일은 없어야 한다.

장비(탐사선 단계, 부품)는 더 이상 확률을 올리지 않는 대신, 미니게임
자체를 너그럽게 만드는 쪽으로 쓴다 — 예를 들어 안전 착륙 속도 임계값을
넓히거나, 궤도 진입의 안전 구간을 넓히거나, 제한 시간을 늘리는 식.
정확히 어떤 수치를 어떻게 완화할지는 구현자가 정한다.

### 재도전

탐사는 기존처럼 몇 번이든 다시 보낼 수 있다 (장비는 소모되지 않음).
미니게임도 매번 다시 플레이한다 — 한 번 성공했다고 다음 시도부터
생략되지 않는다.

### 시각 스타일

기존 다크 글래스 HUD 톤을 유지한다. 착륙 미니게임은 `exploration-button`
/ `#exploration-panel`에 쓴 철강빛 남색+호박 톤을, 궤도 진입 미니게임은
`.sound-toggle` / `.object-search-select`에 쓴 청록 톤을 가져와 두 변형이
서로 다른 느낌을 주도록 한다. 새 WebGL/Canvas 라이브러리는 쓰지 않고,
기존 비행 연출과 같은 방식(DOM 요소 + CSS transition, 입력 루프는
`requestAnimationFrame`)으로 구현한다.

## 제약

- 새 npm 의존성을 추가하지 않는다.
- 세미콜론 없이, 홑따옴표 — 기존 코드 스타일(`CLAUDE.md`)을 따른다.
- `exploration-mission.ts`의 기존 발사~도착 타이밍 상수/로직은 수정하지
  않는다. 미니게임은 그 뒤에 이어지는 새 단계로만 추가한다.
- 키보드 단일 키(예: Space)로 두 미니게임 모두 조작 가능해야 한다 —
  수업 중 설명하기 쉬워야 하므로 조작키를 늘리지 않는다.

## 구현자에게 맡기는 부분

- 정확한 파일 구성 (예: `src/approach-minigame.ts` 신설 등).
- 중력 가속도, 안전 속도/구간 폭 등 천체별 구체적인 수치 — 실제 중력비를
  참고하되 "교실에서 몇 번 해보면 적당히 어려운" 수준으로 튜닝.
- 장비(탐사선 단계·부품)가 미니게임 난이도를 정확히 얼마나 완화하는지.
- 가스 행성에 부품도 추가 게이트로 걸지 여부, 건다면 어떤 부품.
- 제한 시간 정확한 값.
- 실패 문구를 몇 종류로 나눌지와 정확한 텍스트.
- 효과음 추가 여부 (`sound.ts`에 합성음 추가는 선택 사항, 필수 아님).
